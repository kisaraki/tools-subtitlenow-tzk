# Phase 2 — Process Capture

狀態：**本機 19045 核心功能、30 分鐘連續擷取與 300 次重啟驗證通過**。完整應用程式矩陣、實體裝置拔除與服務中斷仍需人工驗收。2026-10-08 使用者指示直接啟動 [Phase 3](phase-3.md)；不將本階段未驗項目視為通過。

基準：Windows 10 22H2 Education，19045.6456，x86_64；Rust 1.98.1 MSVC。設計見 [19045 計畫](windows-10-capture-plan.md)、[ADR 0003](adr/0003-runtime-capture-capability.md)、[ADR 0004](adr/0004-session-owned-capture-process.md)。重現步驟見 [實機測試操作](phase-2-test-procedure.md)。

## 使用方式與最終邊界

先執行 cargo run --locked -- --list-sources，再使用 cargo run --locked -- --capture-pid 1234。來源 PID／程序樹範圍在啟動前與執行中可見，按 Ctrl+C 停止；切換來源先停止，再指定新 PID。範圍包括所選程序與子程序、所有播放端點，不保證瀏覽器單一分頁隔離。

父程序只開啟 query／synchronize 程序 handle，固定使用者指定的 PID。最新 Core Audio 列舉、獨立程序來源確認、原生擷取與正規化都在工作階段專用背景程序。來源確認成功前不建立原生 capture client；背景程序不自行改選來源。沒有音訊工作階段的活著程序亦會回報 InvalidSource，不發布 Running 或交付音訊。

已移除 20348 版本門檻；版本只供診斷。輸出只有狀態與受限效能數據，沒有辨識、翻譯、字幕 UI、雲端、WAV／PCM 輸出或永久內容快取。

| 邊界 | 設計 |
| --- | --- |
| 程序／角色 | 每 Session 一個受 Job Object 管理的 helper；背景擷取、正規化、傳送及父程序接收，共四個角色 |
| 音訊格式 | PCM16、48 kHz、立體聲 → mono f32、48 kHz |
| ring | raw／mono 各 12 格，父程序 mono 12 格；每格最多 960 frames |
| 樣本配置 | 兩端通用 Session 各配置兩個 ring，父程序 raw 未使用；總計最多 180 KiB 樣本配置，非完整 working set 上限 |
| pipe | 匿名本機 pipe；訊息最多 4096 bytes，單次音訊最多 960 samples |
| 背壓 | 傳送可能阻擋，但 capture 只推入有界 ring；滿載淘汰舊資料 |
| 逾期／身分 | 250 ms；Session ID、sequence、frame position、QPC／接收時間；舊 Session 不交付 |
| 原生封包 | 每輪最多 32 個；單一封包接受上限一秒，不宣稱引擎緩衝有相同上限 |
| 啟動／停止 | 啟動期限十秒；關閉 pipe 等待正常停止，500 ms 未退出則終止自有 Job |
| 父程序退出 | KILL_ON_JOB_CLOSE；Job 不包含來源程式或其子程序 |

DEBUG 佇列／淘汰量目前只反映父程序接收與消費端，背景程序完整佇列診斷尚未合併。停止清空佇列並 join；Windows 同步呼叫與排程不具硬即時停止保證。

## 2026-10-08 最終回歸

格式、Clippy（all-targets／all-features、-D warnings）、一般測試、Debug 與 Release 建置均通過。一般測試 **71 項通過、12 項需明確環境或長時間的測試略過**：49 library、11 設定、4 探索、7 啟動。

新增回歸確認：父程序的 OpenProcess 不是音訊來源證明；helper 必須拒絕沒有音訊工作階段的測試程序，保留來源存活、不發布 Running、不產生音訊。既有測試涵蓋 COM／PROPVARIANT 壽命、完成錯誤階段、取消、舊 Session、排序、過載、逾期、IPC 格式與 Job 回收。

十項短時間實機／資源測試，以單一程序、單一測試執行緒串行全部通過：

    cargo test --locked --lib -- --ignored --skip thirty_minute --skip manual_application --nocapture --test-threads=1

測試期間因 Windows 鎖定執行中的 EXE，額外使用 --target-dir target/phase2-verification；該目錄只是已忽略的建置產物。

| 驗證 | 最終結果 |
| --- | --- |
| 真實 PCM、三次啟停、來源退出 | 通過 |
| A 單獨、B 單獨、同時發聲、交換來源 | 通過；目標振幅約 0.031250，非目標頻率低於 0.00025 |
| 靜音時另一程序發聲 | 峰值約 0.000031；容許兩個 PCM16 LSB，避免誤判 dither |
| 既有／新增子程序及根程序退出 | 通過；根程序退出即停止，子程序仍存活亦不繼續 |
| 同 PID 兩個播放端點 | 通過；擷取開始後新增第二端點亦包含；停止第一端點串流後第二端點仍可辨識 |
| 超慢消費端 | 停讀一秒仍為 12 格；淘汰 42,720 frames；恢復讀取年齡約 128.97 ms |
| 背景程序異常 | WorkerExited；來源仍存活；重新啟動使用新的 Session |
| 三批共 300 次重啟 | baseline 163；100／200／300 次皆為 163 |

最終 100 次重啟：停止 P50 31.5578 ms、P95 47.2613 ms、最大 86.9995 ms；開始啟動流程到第一個 PCM P50 110.2916 ms、P95 187.4554 ms、最大 278.5019 ms。這是本機 Debug 測量，不含 STT／翻譯／UI，不是第一個有用字幕的保證。

### 2026-10-08 應用程式短測後複驗

手動測試探針改用正式父程序固定 PID、helper 每次確認來源的邊界；新增 1730 Hz 選項，播放器合成音由五秒延長至三十秒，仍只在 RAM。格式、Clippy、71 項一般測試、Debug 建置與 Node 語法檢查再次通過。十二項測試仍預設略過，另外明確執行的十項短時間原生回歸全部通過（112.27 秒）；本輪沒有重跑三十分鐘測試。

三批 300 次重啟的 handle 為 162 → 162 → 162 → 162。另一次 100 次為 211 → 213，仍在原本兩個暫時 handle 容許量內；停止 P50／P95／最大為 45.6628／61.5853／81.7891 ms，首個 PCM 為 200.615／239.7401／317.879 ms。純探索 217 → 217，mock worker 212 → 212。慢消費端上限仍為 12 格，淘汰 42,240 frames，恢復年齡 135.1764 ms；A／B 與雙端點目標振幅 0.031250，非目標 0.000000。這些結果不能取代下方 Chrome 播放正例失敗的查核。

本輪已確認沒有遺留音源伺服器或 PotPlayer 測試程序；十一份 Markdown 的 UTF-8 與程式碼區塊配對檢查通過。

## 2026-10-07 連續擷取與失敗紀錄

30 分鐘、1,800 秒連續擷取通過；29 次暖機後取樣，交付 84,061,920 frames。該次使用來源確認仍在父程序的舊啟動順序；後續修正只移動啟動前確認，音訊擷取／正規化／傳輸迴圈未變，最終啟動／切換則由 300 次與其他回歸另行驗證。

| 指標 | 暖機 → 最終 |
| --- | --- |
| 父程序 private bytes | 2,322,432 → 2,191,360 |
| helper private bytes | 4,771,840 → 4,706,304 |
| 父程序 handle／thread | 225／9 → 218／4 |
| helper handle／thread | 249／9 → 249／5 |
| 最大父程序 mono 佇列 | 7 格，上限 12 |
| 呼叫起點最大音訊年齡 | 249.9418 ms |
| 回傳後觀測最大年齡 | 256.2108 ms，包含執行緒排程延遲 |
| 每分鐘單核心 CPU 百分比最大值 | 父程序 3.591%／helper 3.680% |
| 停止 | 35.8787 ms；佇列清空、helper 已退出 |

第一輪約 567 秒時，測試用「取出後的時間」判斷 250 ms freshness，加五毫秒容許仍失敗。修正測試為取出呼叫起點驗證已逾期資料不得交付，另外量測回傳後年齡；沒有放寬產品的 250 ms 策略，並完整重跑 30 分鐘。CPU 為每分鐘累計時間差、單核心基準，不是瞬間最大值；COM 參照數未直接全程量測。

早期同程序 native client 100 次留下約 200 個 Timer；已修正 AgileReference 0x80040155 與借用 PROPVARIANT 被自動 Drop 提早釋放 Box 的程式錯誤，Timer 現象仍促成 ADR 0004。未宣稱修改 Windows 元件內部。

後續才發現父程序反覆建立完整來源確認也會使短測試 handle 增加：一輪 214 → 218，三批測試在第二批 216 → 218 → 220 失敗。只關閉來源建立通知仍失敗，該試驗已撤回。保留測試來源資料但由 helper 每次重新確認的診斷 300 次穩定；加入長時間間隔亦顯示部分資源會延後回收。未以這些診斷模式冒充正式路徑。

最終將全部啟動前 Core Audio 確認移入既有 Session helper，父程序只固定 PID／程序 handle；正常路徑 300 次皆為 163，原本兩個暫時 handle 的容許量未提高。診斷環境開關與等待模式已移除。WinDbg 只查詢資源類型與堆疊，沒有傾印或音訊檔。

2026-10-05 的 UnsupportedWindows 只是本程式版本門檻，未呼叫 API。當時 58 項一般測試與硬體略過結果保留為歷史，不能證明 OS 不支援或已完成擷取。
