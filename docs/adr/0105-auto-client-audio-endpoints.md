# ADR 0105：Auto 送出本機音訊收尾要求，不等待首個轉錄

日期：2026-10-26。狀態：採用，Phase 11 延遲修正；工程檢查通過，真實延遲仍待人工驗收。

## 問題與證據

使用者確認本次裝置切換、重新開始與停止測試正常，但回報 Gemini Transcribe Live／Auto 在開始及長停頓後，連英文原文都約三十秒才出現，另有較多翻譯逾期。未取得延遲當下的計數，不能認定所有延遲或翻譯丟棄都有同一根因。

現有 Gemini 路徑忽略預處理的本機音訊端點。輸入閒置收尾只適用於傳輸停止；來源持續送靜音封包時不會觸發。語言收尾則須先收到未確認語言的轉錄，無法幫助尚無第一個轉錄的情況。新增測試檢查「首個轉錄之前的本機端點也應送達服務」。

## 決定

僅 Gemini Transcribe Live／Auto 使用既有預處理的能量端點：RMS 低於 0.003 持續四百毫秒，或連續音訊達四秒時，於對應 PCM 之後送 audioStreamEnd。四秒是有界音訊區段要求，不稱為語意句尾或語音偵測。不中斷後續新鮮 PCM、不另建連線、不默選語言；明選語言、Live Translate 及 OpenAI 路徑不變。

官方 [Live transcription / Hybrid VAD](https://ai.google.dev/gemini-api/docs/live-api/live-transcribe#hybrid-vad) 說明保留服務自動起點並由客戶端送 audioStreamEnd 提示收尾。本機端點不建立服務 utterance、不自行定稿、不提供媒體時間或來源語言證據。服務真正 final 才退休段落；本機語言備援與標記優先、八秒等待上限、取消及 Session 隔離保持。

已因語言等待送過收尾時，同一等待不重送。已收尾後的純靜音不重新啟動傳輸閒置收尾計時；新活躍音訊可再次開啟計時。診斷僅增加「本機音訊收尾要求」成功送出數，不能當成收到轉錄或翻譯成功。

## 驗證與限制

以協定測試及 localhost WebSocket 合成音訊驗證：服務在收尾前不回轉錄時，開始及停頓後仍能收到收尾並交付經語言核對的真正 final；持續音訊不中斷，靜音不反覆要求，其他模型及明選語言不變。沿用無內容持久化與原有有界佇列／預處理 worker。

這不是實際 Gemini 延遲基準。真實首句延遲及逾期丟棄改善仍需使用者於新版測試；不放寬三秒翻譯年齡來掩蓋延遲。

最終 114 項定向包含六項新增，獨立完整回歸 2135 一般成功、零失敗、18 ignored；格式／零警告 Clippy／Debug／Release 通過。已備份及更新標準版並開啟待命，詳細數據見 [診斷紀錄](../phase-11-gemini-diagnostics.md)。能量門檻及四秒區段可能切開語意句子，不能當作語音語意模型或準確率保證；仍保留服務暫定修訂及真正定稿。
